# 🪝 Frida 魔改接入 wxshadow：把常见 Hook 痕迹压到更低

[📖 繁體中文](readme.md)　|　[📖 简体中文](readme_cn.md)

这篇内容不是单纯记一次 patch，而是把 Frida 接入 wxshadow 时真正会卡住的几个关键点拆开整理：从 patch 方式本身，到 `libart.so` 的 huge PMD 兼容，再到系统库默认 hook、maps 与 `memfd` 这些容易留下特征的位置。

它的价值在于，文章不只停在「改过了」，而是把哪些部分已经推进、哪些只做到局部收敛、哪些仍然留有缺口说清楚。对想把 Frida 行为收敛得更可控的人来说，这种边界感比单点技巧更重要。

## 🔎 这次处理到哪里

| 范围 | 文中实际处理的方向 | 目前能看到的结果 |
| --- | --- | --- |
| wxshadow 集成兼容 | 调整 patch 形式，避开同页 literal 带来的死循环 | 直接接入时会卡死的问题被拆清，并给出可落地的改写方向 |
| `libart.so` Huge PMD | 针对 file-backed THP 补上手动 demotion 思路 | 原本容易失败的 hook 路径被推进到可处理状态 |
| Frida 默认 hook | 重新梳理 `libc.so`、`libart.so` 等默认行为，让部份路径改走 wxshadow | 默认 hook 痕迹不再只能靠原生 patch 流程处理 |
| maps / `memfd` 特征 | 收敛系统库 `rwxp` 暴露，并追到 `memfd` 来源 | 有些特征能进一步压低，但仍有残留部份需要另外处理 |

## 🧩 这篇重点在看什么

重点不是逐段展示 patch 细节，而是把 Frida 与 wxshadow 接到一起时，真正会影响稳定性和可见痕迹的几个交界面讲清楚。像是 live lock、`libart.so` 前段 huge PMD、Frida 16 与 17 的默认 hook 差异，这些都直接影响方案能不能稳定落地。

文中也提到，Frida 17.9.3 在一些样本上表现不稳，因此后续主线仍回到较熟悉的 Frida 16 路线继续处理。这让整篇不只是功能堆叠，而是把版本取舍和兼容边界一起交代清楚。

## ✅ 哪些结果值得看

文中能看到的成果，是把一部分系统库默认 hook、主动 hook API、maps 特征与 `memfd` 暴露收敛到更可控的范围，同时也明确保留了未解决区域，例如 `libandroid_runtime.so`、`libselinux.so`，以及匿名 `rwxp` 回调页这类残留痕迹。

这让整篇更像是一份可延伸的改造记录，而不是把局部结果包装成完整终局。对读者来说，知道哪些地方已经有路，哪些地方还得再补，反而更有参考价值。

## 🎯 适合谁看

如果你正在做 Frida 魔改、想把默认 hook 路径改得更隐蔽，或者正在追 `libart.so`、maps、`memfd` 这几类常见暴露点，这篇会比较有参考价值。

## 💬 一句话说完

这篇把 Frida 接入 wxshadow 时最关键的兼容与暴露问题，收敛成一条更可验证、也更方便继续往下改的路线。
