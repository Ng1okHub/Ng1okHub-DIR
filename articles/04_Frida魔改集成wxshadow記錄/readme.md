# 🪝 Frida 魔改接入 wxshadow：把常見 Hook 痕跡壓到更低

[📖 繁體中文](readme.md)　|　[📖 简体中文](readme_cn.md)

這篇內容不是單純記一次 patch，而是把 Frida 接入 wxshadow 時真正會卡住的幾個關鍵點拆開整理：從 patch 方式本身，到 `libart.so` 的 huge PMD 兼容，再到系統庫默認 hook、maps 與 `memfd` 這些容易留下特徵的位置。

它的價值在於，文章不只停在「改過了」，而是把哪些部分已經推進、哪些只做到局部收斂、哪些仍然留有缺口說清楚。對想把 Frida 行為收斂得更可控的人來說，這種邊界感比單點技巧更重要。

## 🔎 這次處理到哪裡

| 範圍 | 文中實際處理的方向 | 目前能看到的結果 |
| --- | --- | --- |
| wxshadow 集成兼容 | 調整 patch 形式，避開同頁 literal 帶來的死循環 | 直接接入時會卡死的問題被拆清，並給出可落地的改寫方向 |
| `libart.so` Huge PMD | 針對 file-backed THP 補上手動 demotion 思路 | 原本容易失敗的 hook 路徑被推進到可處理狀態 |
| Frida 默認 hook | 重新梳理 `libc.so`、`libart.so` 等默認行為，讓部份路徑改走 wxshadow | 默認 hook 痕跡不再只能靠原生 patch 流程處理 |
| maps / `memfd` 特徵 | 收斂系統庫 `rwxp` 暴露，並追到 `memfd` 來源 | 有些特徵能進一步壓低，但仍有殘留部份需要另外處理 |

## 🧩 這篇重點在看什麼

重點不是逐段展示 patch 細節，而是把 Frida 與 wxshadow 接到一起時，真正會影響穩定性和可見痕跡的幾個交界面講清楚。像是 live lock、`libart.so` 前段 huge PMD、Frida 16 與 17 的默認 hook 差異，這些都直接影響方案能不能穩定落地。

文中也提到，Frida 17.9.3 在一些樣本上表現不穩，因此後續主線仍回到較熟悉的 Frida 16 路線繼續處理。這讓整篇不只是功能堆疊，而是把版本取捨和兼容邊界一起交代清楚。

## ✅ 哪些結果值得看

文中能看到的成果，是把一部分系統庫默認 hook、主動 hook API、maps 特徵與 `memfd` 暴露收斂到更可控的範圍，同時也明確保留了未解決區域，例如 `libandroid_runtime.so`、`libselinux.so`，以及匿名 `rwxp` 回調頁這類殘留痕跡。

這讓整篇更像是一份可延伸的改造記錄，而不是把局部結果包裝成完整終局。對讀者來說，知道哪些地方已經有路，哪些地方還得再補，反而更有參考價值。

## 🎯 適合誰看

如果你正在做 Frida 魔改、想把默認 hook 路徑改得更隱蔽，或者正在追 `libart.so`、maps、`memfd` 這幾類常見暴露點，這篇會比較有參考價值。

## 💬 一句話說完

這篇把 Frida 接入 wxshadow 時最關鍵的兼容與暴露問題，收斂成一條更可驗證、也更方便繼續往下改的路線。
